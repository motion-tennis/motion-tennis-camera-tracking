# Camera-tracking staged workflow

[Repository home](../README.md) · [Orientation](orientation.md) · [Canonical status](https://github.com/motion-tennis/documentation/blob/main/docs/project-status.md) · [Shared stages](https://github.com/motion-tennis/documentation/blob/main/docs/project-stages.md) · [Task and handoff template](https://github.com/motion-tennis/documentation/blob/main/docs/contribution-workflow.md)

This table maps shared stage IDs to tracking work. The central status is the sole active-stage authority; the table is neither an independent schedule nor automatic authorization to build future modules. Every task names one stage and a bounded deliverable, allowed files, acceptance evidence and deferred work. Local evidence contributes to the shared gate without advancing it on its own.

| Stage | Scoped tracking deliverable | Verifiable exit evidence | Explicitly deferred work |
| --- | --- | --- | --- |
| **S0 — Shared contract/coordination baseline** | Review image-space pose, identity/session, timestamp/quality, body-local 2.5D and versioned match/roster dependencies; plan fixtures/handoffs and add small contract/codec validation tools only when explicitly tasked | Recorded contract decisions and unresolved evidence; generated-codec compatibility/size/resource results for the tasked slice; documentation checks and central gate status | Capture/model runtime, runtime codec integration, live inference/publishing and a playable game; small contract-validation fixtures remain distinct |
| **S1 — Isolated minimal component slices and fixtures** | Separately authorized file/synthetic adapter and bounded pose/identity/timestamp/2.5D interface slice; no real-camera claim | Reproducible labeled input fixtures, deterministic outputs for missing/invalid identity/timing/joints, and actual local test/run commands for the slice | Live Windows/GPU/camera integration, transport feasibility, end-to-end play and metric true 3D |
| **S2 — Feasibility and transport** | Actual Windows camera/GPU four-person feasibility, model/provider manifest, calibration/timestamp characterization and bounded pose transport against explicit receivers/stubs | Verified provider and artifact/license provenance; full-body focus/FOV, four-person pose rate/identity and exposure uncertainty records; skips/loss and calibration residuals retained | An integrated playable game, complete controller RTT claims, shared-state scoring and the final matched A/B campaign |
| **S3 — One-controller integrated diagnostic transaction** | Real tracking feeds a confirmed person/controller pair, Pi time maps/uncertainty and historical IMU alignment through required ball query/response, atomic commit/feedback and marker links | Complete source-frame/person-to-transaction trace; valid/stale/occluded/restart cases; correct source-time/map provenance and explicit failures | Four-player match claims, automatic AI substitution, additional rule/UI work unrelated to this diagnostic slice |
| **S4 — Four-controller 2v2 playable game** | Four stable confirmed person/controller/avatar bindings and body-local racket/serve observations while Pi independently moves avatar roots automatically, under the reviewed extended contract | Four-person identity through occlusion/crossing and court-end/role changes; ordinary continuous camera/200 Hz input during serving; match fixtures shared with Pi/game/controller owners | Matched full load/fault/topology acceptance, production packaging, alternate backends and true 3D |
| **S5 — Matched topology, load, fault and timing validation** | Tracking/replay load participates in matched external-AP versus Pi-hotspot trials, with four-person inference and both views active | Shared repeated-run manifests, frame/inference/age distributions, identity failures, uncertainty/skip/loss counters and fault recovery; identical declared camera/model/workload across variants | Silent model/rate/quality changes to improve one variant, unverifiable timing claims and unrelated feature expansion |
| **S6 — Reproducible demonstrator** | Pin validated camera/model/runtime/calibration configuration and real install/start/diagnostic/recovery procedures | Another contributor reproduces the declared setup/results using recorded revisions/artifacts and appropriate test data; limitations remain explicit | Unapproved model/device changes, new gameplay and deferred depth/stereo/true-3D work |
| **S7 — Deferred true 3D/alternatives** | Only an explicitly authorized depth/stereo/multi-view or alternative-model experiment with a separate calibrated profile | Named experiment proposal, license/compatibility review, metric geometry/identity/timing evidence and explicit migration impact | Automatic work after S6, guessed monocular depth in the current schema or wholesale replacement of the baseline |

Use the shared [contribution workflow](https://github.com/motion-tennis/documentation/blob/main/docs/contribution-workflow.md) for baseline revision/status, dependencies, acceptance evidence and handoff. An explicit human request for a named later-stage slice is a bounded exception: record its limits and missing prerequisites, and leave the global stage unchanged. Routine fixes within an authorized slice do not need repeated approval.

If canonical status is unavailable, use a pinned verified status/revision supplied with the task and record that limitation. Do not infer runtime authorization from this table. Finish the scoped deliverable and checks, then hand off the next proposed slice without starting it automatically.
